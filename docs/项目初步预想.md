# 个人AI项目（偏前端）初步设想

> 我觉得“AI 多文档阅读与协作助手”这个方向不错，但是光这个标题太大众了，我想做一个支持多类型文件，如“复制过来的纯文字”、“网站视频链接”、“图片”、“网站图片链接”、“markdown文档”，“网站链接”以及传统的office文件，主要功能是自动爬取并总结网站的内容，并且结合上传的文件自动归并为本地的RAG知识库，相当于在人为定下的知识边界内，去推理、解释、总结出想要的信息。并且可以支持多agent协作，你看怎么样合适？

> 后续想支持代码文件也支持，但是代码文件单个提交意义不大，若整个项目完整提交，如何识别或总结有待商讨，初步的设想是通过skill来总结项目，连同代码写入RAG库。

这个方向比普通的“多文档聊天助手”更有辨识度。它的核心不应只是“支持很多格式”，而应该强调：

把分散在文件、网页、图片和视频中的内容自动采集、解析、归一化，并建立一个具有明确知识边界、可追溯引用、可由多个 Agent 协作推理的本地知识空间。

这样定位后，它就不再只是“上传文件然后问答”，而是一个完整的：

```text
多源内容采集 → 内容解析 → 知识归并 → 边界检索
→ 多 Agent 分析 → 引用溯源 → 协作沉淀
```

我认为非常适合作为 Vue 3 + TypeScript + FastAPI + SSE + WebSocket 的综合型项目。

## 一、建议重新定义项目，不要叫“多文档阅读助手”

“多文档”会让人第一反应是 PDF、Word 问答，无法体现网页采集、视频解析、本地知识边界和多 Agent。

可以定位为：

### 产品定位

面向多源异构内容的边界知识研究与协作平台

或者用通俗一点的描述：

用户将文件、文本、网页、图片和视频链接投放到一个知识空间中，系统自动完成采集、解析、摘要、分类、去重和知识库构建。用户可要求多个 AI Agent 在指定知识边界内进行检索、对比、解释和总结，并查看每个结论对应的原始证据。

这里最关键的差异点是三个：

1. 多源内容自动归一化
2. 在指定知识边界内回答
3. 多 Agent 基于证据协作，而不是自由发挥

## 二、项目名称建议

可以采用“产品名 + 技术副标题”的方式。

### 方案一：界知 BoundaryMind

比较符合“知识边界”的概念。

**界知 BoundaryMind**——多源知识归并与多智能体研究平台

技术标题：

基于 Vue 3、FastAPI 和本地 RAG 的多源知识边界推理与多智能体协作平台

### 方案二：知域 KnowledgeScope

强调用户人为划定知识范围。

**知域 KnowledgeScope**——基于证据的知识空间与 AI 研究助手

适合功能表达：

一个知识空间，就是一个独立的知识边界。

### 方案三：源析 SourceLens

强调从多个来源中采集、分析、溯源。

**源析 SourceLens**——多源内容采集、归并与智能研究工作台

比较适合偏研究、信息分析场景。

### 方案四：织识 WeaveMind

强调将碎片内容编织成知识网络。

**织识 WeaveMind**——多模态知识编织与 Agent 协作平台

适合后续加入知识图谱。

### 方案五：域见 ScopeInsight

**域见 ScopeInsight**——边界知识推理与多源研究助手

更偏产品化。

### 我的推荐

正式项目名称可以定为：

**知域 KnowledgeScope：基于本地 RAG 的多源知识归并与多智能体协作平台**

这个名字能覆盖：

- 多类型内容；
- 本地知识库；
- 人工划定知识边界；
- Agent 协作；
- 检索、推理和总结。

## 三、核心产品模型：知识空间

建议不要把产品中心设计成“聊天会话”，而要设计成知识空间 Workspace。

例如用户创建：

- 新能源汽车行业研究
- Vue 3 技术资料库
- 某公司竞品分析
- 毕业论文参考资料
- 产品需求与用户反馈

每个知识空间拥有独立的：

- 数据源；
- 文件；
- 网页；
- 图片；
- 视频链接；
- 文本片段；
- 向量索引；
- Agent 配置；
- 会话记录；
- 权限成员；
- 知识边界。

用户提问时必须选择知识空间：

> 请只根据“新能源汽车行业研究”空间中的资料，  
> 对比三家公司的技术路线，并标明依据。

这就是你的产品与普通 AI 问答的明显差异。

## 四、支持的数据源如何统一

你列出的类型很多，建议在系统内部统一抽象成：

```ts
type SourceType =
  | 'plain_text'
  | 'web_page'
  | 'video_url'
  | 'image'
  | 'image_url'
  | 'markdown'
  | 'pdf'
  | 'word'
  | 'excel'
  | 'powerpoint'
```

无论用户输入什么，最终都进入统一的数据管道：

```text
原始数据 Source
    ↓
采集 Fetch
    ↓
解析 Parse
    ↓
文本/结构/图片提取
    ↓
清洗与标准化 Normalize
    ↓
摘要与元数据生成
    ↓
分块 Chunk
    ↓
Embedding
    ↓
本地向量库
    ↓
检索与引用
```

### 1. 复制的纯文字

处理最简单：

- 保存原文；
- 自动识别标题；
- 生成摘要和标签；
- 按段落分块；
- 写入知识库。

用户可以给文本命名：

- 来源名称：会议临时记录
- 来源类型：手动文本

### 2. 网站链接

后端负责：

- 下载网页；
- 提取正文；
- 去除导航、广告、页脚；
- 保留标题、作者、发布时间和 URL；
- 生成 Markdown；
- 摘要、切片、向量化。

可使用：

- `httpx`：普通网页请求；
- `BeautifulSoup`：HTML解析；
- `trafilatura`：正文提取；
- `Playwright`：动态渲染网页；
- `readability-lxml`：正文抽取。

需要区分两种模式：

- **单页面采集**：只解析当前 URL
- **站点采集**：按规则继续抓取站内链接

站点采集必须提供限制：

- 最大层级；
- 最大页面数；
- URL 白名单；
- URL 排除规则；
- 同域限制；
- 请求间隔；
- 是否允许 JavaScript 渲染。

不要默认无限爬取。

### 3. 网站视频链接

视频不能简单理解为“下载后总结”，建议拆成：

- 视频元数据
- 字幕
- 音频转写
- 关键帧
- 页面简介
- 评论或章节信息（可选）

处理优先级：

```text
官方字幕
→ 自动字幕
→ 音频 ASR 转写
→ 关键帧 OCR/VLM
```

最终生成：

```markdown
# 视频标题

## 基本信息
- 来源URL
- 作者
- 发布时间
- 时长

## 视频摘要

## 时间轴
- 00:00 主题介绍
- 03:25 核心概念
- 08:40 案例分析

## 完整转写

## 关键画面
```

需要注意：视频平台的接口、版权、登录限制和反爬策略不同。项目 MVP 不宜承诺支持所有视频站点，可以先支持：

- 可直接访问的公开视频链接；
- 用户提供字幕文件；
- 用户上传本地音视频；
- 某一两个明确适配的平台。

### 4. 图片和网站图片链接

图片处理可以包含：

- OCR 文字提取；
- VLM 图像理解；
- 图表解释；
- 图片摘要；
- 图片中的实体识别；
- 保存原图及来源链接。

图片不要只存一段模型描述，建议保留两类内容：

```json
{
  "ocrText": "图片中实际识别出的文字",
  "visualDescription": "模型对图片内容的语义描述"
}
```

回答时也要区分：

- 原图文字证据
- AI 图像理解结果

避免把模型描述误认为原始事实。

### 5. Markdown 和 Office 文件

可以支持：

- Markdown：保留标题层级和代码块；
- PDF：正文、页码、图片、表格；
- Word：标题、段落、表格、图片；
- Excel：工作表、表头、数据区域；
- PPTX：幻灯片标题、文本、备注、图片和页码。

Office 文件不能全部使用同一种固定分块策略。

例如：

- Word/PDF：按标题和段落分块
- PPTX：按幻灯片分块
- Excel：按工作表、表格区域分块
- Markdown：按标题层级分块
- 视频：按时间段分块
- 网页：按语义章节分块

这是项目比较有价值的技术点。

## 五、“知识边界”应该成为核心功能

“只在指定范围内回答”不能仅靠一句 Prompt 实现，应该在产品和检索层共同约束。

### 1. 空间级边界

用户只能选择当前知识空间中的内容：

```text
新能源汽车空间
├── 行业报告
├── 政策网页
├── 企业财报
└── 专家视频
```

检索时强制添加：

```json
{
  "workspaceId": "workspace_001"
}
```

### 2. 来源级边界

用户还可以进一步选择：

- 仅根据选中的5份财报回答
- 排除视频来源
- 仅使用2025年之后的内容
- 只使用官方来源

检索条件可以是：

```ts
interface KnowledgeScope {
  workspaceId: string
  sourceIds?: string[]
  sourceTypes?: SourceType[]
  tags?: string[]
  timeRange?: {
    start?: string
    end?: string
  }
  trustLevels?: Array<'official' | 'verified' | 'general'>
}
```

### 3. 回答模式

建议提供三种模式：

#### 严格边界

只能根据知识库证据回答。

没有证据时明确回答“当前知识空间中未找到相关依据”。

#### 边界优先

优先使用知识库，知识不足时允许补充通用知识，但必须明确区分。

#### 开放研究

允许联网搜索，并将新来源经过用户确认后加入知识空间。

这个设计很有产品感，也能解决用户对于“AI 是否在瞎编”的疑问。

## 六、多 Agent 不要只做成多个头像聊天

多 Agent 最容易沦为“同一个模型换了几个名字”。建议按实际职责拆分。

### 推荐 Agent 架构

#### 1. 任务规划 Agent

负责：

- 理解用户问题；
- 拆解任务；
- 决定调用哪些 Agent；
- 编排执行顺序；
- 汇总任务状态。

例如：

```text
用户：对比三份报告中对AI行业风险的判断。

规划结果：
1. 检索三份报告中的风险章节
2. 分别提取观点
3. 对齐比较维度
4. 检查观点是否有原文依据
5. 生成对比报告
```

#### 2. 检索 Agent

负责：

- 改写查询；
- 多轮检索；
- 混合召回；
- 检索不足时调整关键词；
- 返回引用片段。

#### 3. 内容分析 Agent

负责：

- 阅读检索结果；
- 提取观点和数据；
- 识别冲突；
- 形成结构化分析。

#### 4. 事实核验 Agent

负责：

- 检查每个结论是否有来源；
- 检查引用与结论是否一致；
- 标记证据不足；
- 发现不同来源间的矛盾。

#### 5. 报告生成 Agent

负责：

- 根据分析结果生成最终内容；
- 输出摘要、表格、报告或思维导图；
- 插入引用标记。

#### 6. 数据接入 Agent

可以作为后台 Agent：

- 识别来源类型；
- 选择解析工具；
- 评估内容质量；
- 生成标签；
- 判断是否重复；
- 写入知识库。

### 多 Agent 工作流示例

```text
用户问题
   ↓
Planner：拆解任务
   ↓
Retriever：检索多个来源
   ↓
Analyst：提取和对比观点
   ↓
Verifier：检查证据和冲突
   ↓
Writer：生成带引用报告
```

前端可以将这个过程做成可视化任务链：

```text
✓ 任务规划
✓ 检索到 18 个相关片段
● 正在比较三个来源
○ 等待事实核验
○ 等待生成报告
```

这比普通聊天框更有展示价值。

## 七、SSE 在这个项目中非常合适

SSE 不仅用来输出文字，还可以传输整个 Agent 工作流。

### 事件设计示例

```text
event: task_started
data: {"taskId":"task_001"}

event: plan_created
data: {
  "steps":[
    {"id":"step_1","name":"检索资料"},
    {"id":"step_2","name":"对比观点"},
    {"id":"step_3","name":"核验引用"}
  ]
}

event: agent_started
data: {
  "agent":"retriever",
  "stepId":"step_1"
}

event: source_found
data: {
  "sourceId":"source_12",
  "title":"2026行业报告",
  "page":18
}
```
